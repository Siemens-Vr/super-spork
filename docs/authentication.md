# Authentication and authorization

All state-changing `/api/v1` requests require a synchronizer CSRF token, including registration, password recovery and login. Call `GET /auth/csrf` with a cookie jar, retain the returned cookie, and send `X-CSRF-Token`. Disallowed Origin headers are rejected. CORS origins are explicit. Same-origin Swagger requests obtain a current token automatically; ordinary clients must refresh after session rotation.

Sessions use maintained `express-session` with a Prisma-backed server store. Cookies are HTTP-only, SameSite=Lax, scoped to `/`; production adds Secure and the `__Host-` prefix. Session expiration is absolute and configurable (12 hours by default). Login, reauthentication and MFA rotate session identifiers and CSRF secrets. Password recovery, logout-all and administrative status changes revoke all sessions and increment a session version to invalidate stale concurrent sessions. Active sessions can be listed and individually revoked only by their owner. Set proxy hops to the exact deployment topology; trusting arbitrary forwarded IPs weakens rate limiting.

Registration normalizes email and Kenyan/default E.164 phone numbers, requires the current privacy notice version and accepts 12–128-character passphrases. Argon2id uses 64 MiB, three iterations and one lane. An applicant cannot choose roles. Public registration and reset/resend requests use generic responses; duplicate registration creates no additional account. Login failures use a uniform error, with a dummy Argon2 hash for unknown accounts.

OTP challenges use cryptographic six-digit generation and keyed SHA-256 verifiers bound to purpose and challenge ID. Default expiry is five minutes, maximum attempts five and resend cooldown one minute. Challenge verification locks the user; failed attempts commit even when the API rejects the code. A new challenge invalidates old codes, and successful codes are consumed once. Network and account limits are enforced atomically in PostgreSQL. Purpose-bound recovery cannot verify email, does not create a password for Google-only accounts and does not reactivate suspended/closed accounts. Password recovery consumes its code together with the password change and session revocation in one transaction, and queues a security notification.

Google uses `https://accounts.google.com` discovery, an exact configured callback `${APP_URL}/api/v1/auth/google/callback`, authorization code grant, state, nonce and S256 PKCE. openid-client validates signed ID-token claims including issuer/audience/expiration; the application also requires `email_verified === true`. Secrets and pending state live in the server session. Callback flow state expires after ten minutes and is consumed. New Google applicants complete phone and consent collection. Existing provider subjects sign in directly. Matching email without a linked subject produces `ACCOUNT_LINK_REQUIRED`. To link, log into the existing account, reauthenticate within five minutes, and POST `/auth/google/link`. A Google-only user can reauthenticate by signing in through their already-linked Google identity. Google tokens are never used as application sessions or persisted as application credentials.

Admins are provisioned by an authorized shell operator. No public endpoint creates roles or admins. Admin login can access its own authentication/MFA endpoints but cannot use privileged routes before MFA. POST `/auth/mfa/setup` after a recent login, add its provisioning URI to an authenticator, save recovery codes once, then POST `/auth/mfa/verify` with a TOTP. Subsequent logins use `/auth/mfa/verify` directly. MFA secrets use AES-256-GCM encryption; recovery codes are keyed hashes and consumed transactionally; accepted TOTP counters cannot replay. MFA expires for privileged access after 30 minutes by default. Authenticator replacement after losing all factors requires the institution's verified operator recovery procedure; no weak public bypass exists.

## Initial permissions

| Role      | Permissions                                                                                                                                           |
| --------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| APPLICANT | `profile.read.self`, `profile.update.self`, `documents.upload.self`, `documents.read.self`, `assessments.schedule.self`                               |
| ADMIN     | `documents.verify`, `documents.review`, `industries.manage`, `companies.manage`, `careers.manage`, `assessments.manage`, `users.manage`, `audit.read` |

Admin routes require both role and the relevant permission. Institution management uses `documents.review`; competency and framework management use `careers.manage`; availability/blueprints/bookings use `assessments.manage`. Applicant services additionally constrain records by the authenticated user ID. Authentication identity responses expose only safe profile and permission fields.
